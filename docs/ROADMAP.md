# Maintenance roadmap

This is a proposed sequence, not a promised release date or support SLA. Source distribution and MIT licensing were authorized on 2026-10-24; any support-program role, maintenance commitment or future scope must reflect actual work.

1. **First public candidate:** confirm source rights and license, establish a separate repository, configure a real support/security contact, review the explicit publication file list and publish the reproducible Windows test results.
2. **Feedback-driven maintenance:** reproduce real user issues with synthetic fixtures; prioritize busy-work protection, shutdown failures, installation/removal clarity and Windows compatibility. Record actual reviews, fixes and release notes.
3. **Adapter examples:** add one integration at a time only where ownership, queued/active work and supported normal close can be verified. Keep production/shared tools excluded unless a separate design and authorization changes that scope.
4. **Portability:** assess other operating systems against equivalent identity and permission guarantees. Do not claim cross-platform support from a JavaScript-only helper or a skipped Windows test.

Codex support, if granted, would assist code review, reproductions, isolated tests, issue triage and integration documentation. Running the toolkit requires no OpenAI API. An API-based maintainer workflow would need a concrete use case and a separate decision; no API dependency is planned just to obtain credits.

Project health should be described through verified maintenance work and real user feedback. Do not fabricate downloads, stars, adoption, savings or a guaranteed benefit from an open-source support program.
